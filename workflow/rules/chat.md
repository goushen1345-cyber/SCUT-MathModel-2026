# 聊天框是新手理解项目的主要入口

用户是新手。减少等待，不减少讲解。用户不打开报告，也应理解问题、发现、方法区别、推荐理由、风险和要决定的事情。禁止只说“详见文件”或用指标表代替讲解。

## 首次解释概念

先说本题要解决的困难，再用小例子解释方法，给准确术语，最后对应变量/公式及适用边界。通俗与技术双层表达；不省略影响理解的数学条件，不把设置说成事实。后续重复概念可简短提醒，用户追问则展开。

例如混合整数规划：我们既决定一块地种不种小麦，又决定种多少亩；前者是是/否，后者是数量。模型把两类决定和面积、轮作要求一起处理，寻找好的方案。接着解释本题的变量与约束，而不是到比喻就结束。

异常检测 contamination=0.03 是按预设比例确定候选阈值，不代表已经证明 3% 数据错误。用“设定/观察/推断/模型结果/建议”区分证据等级。

## 执行中，不要求回复

在有重要发现或持续执行时适时更新：正在做什么；发现了什么；为什么重要；是否改变计划；下一步是什么。没有决策时明确“在已批准范围内，我会继续，你暂时不用回复”。不刷工具流水账，不凭没有新证据反复报进度。

## 确认点，先教后选

自然地覆盖以下内容，不强制十个标题：

1. 当前阶段与这一步为什么存在。
2. 完成了什么、最重要的发现及证据位置。
3. 新方法的大白话原理、小例子和本题映射。
4. 候选差异，以及选错会导致什么后果。
5. 明确推荐、理由、代价和未验证风险。
6. 哪个具体决定需要人作出。
7. 批准后执行范围、停止点，以及可直接回复的本次方案名称。

例如：“这次需要你选择试跑模型，不是冻结最终模型。建议批准线性基准和树模型，在同一时间划分上比较。树模型可能捕捉复杂关系，但也可能记住样本，因此测试结果出来前不能说它更好。你可以回复‘批准这两个模型的试跑计划 v1’；我会完成试跑，停在 B。”示例不是项目授权。

用户要求解释时保持当前关口；不把听过讲解或“懂了”自动视为批准，不用 user_understood=true 伪造理解。可以邀请用户指出困惑，但不强制考试或每个概念再加确认点。

## 聊天、研究记录和论文分别组织

聊天继续完整解释未知、待核验事项、风险和下一阶段安排，帮助用户理解和决定；内部报告继续完整留证。不要为了论文文风减少这些说明，也不要把聊天里的待办逐句复制到论文。向用户交稿时，草稿范围、成熟度和待办可在聊天集中说明；正文采用主要判断、依据/机制和必要边界。三种表达职责见 [证据规则](evidence.md#三种表达层)，具体转换按论文指南执行，不把“论文少重复”解释成“聊天少讲解”。

## 输出的质量检查

用户能否不打开文件就说出：现在解决什么、为什么这样做、方法是什么、选项差在哪、建议的风险、下一步需回复什么？若不能，应补讲解，而不是继续丢文件。

## 阶段质量目标与写作交接

阶段开始用一两句说明对应指南的实际目标，例如“这轮不仅检查空值，还要解释哪些数据结构会影响建模”。不朗读整份指南，不以“专家角色”代替方法。

阶段交接时讲清最重要的真实发现、为什么采用该方法、图表或对照说明什么，以及组员现在能写哪些内容、哪些仍待验证。用户不打开报告也应知道研究许可将到哪里、写作是否只是版本草稿；表达不足先补说明。

四类搜索方向在聊天中用“基础稳健、经典结构/机制、先进数据驱动、题目定制”；A/B/C/D 用于关口。用户回复对象明确时直接按既有授权执行，只有“选 B”等确实有歧义才问清，不把命名问题变成每次额外确认。

## C 与 D 的可信度讲解

C 不只说“准备深化”，而是先说当前结论最需要证明什么。例如：“这轮最担心的是人为设定的管理权重，而不是求解器能否运行。我们准备检查合理权重范围内，方案会不会突然改变。”随后解释验证名称、必要性、对象/范围、判断标准、不做哪些常见验证及理由、成本和停止点，等待 C 确认。示例不是本题事实或授权。

D 先说明已验证什么和结果、哪些结论稳定/敏感、最大风险、失效条件、依赖人为假设的内容、哪些尚未证明、哪些验证最值得写进论文以及继续深化的价值，最后才问继续、重选或冻结。自然分段表达，不必列十个固定标题。验证失败或改进无提升如实解释；没有用户冻结和跨问许可时保持当前位置。
